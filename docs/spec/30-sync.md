# 동기화

서버가 유일한 원본, 기기(데스크톱 앱·반응형 웹, 이후 모바일)는 캐시. 충돌은 데이터 유형별 규칙 하나로 자동 처리하고, 사용자에게는 결과만 해요체 한 줄로 알림. 사실값·제안·함께 모드 규칙은 → 핵심 규칙 › 부부·제안·권한을 따르고 이 탭은 동시에 일어날 때의 처리만 정함.

## 1. 원칙

- 단일 원본: 확정 값·계산 결과(배분, 안 나눈 돈 재계산, 목표 진행)는 서버 값이 기준. 앱의 계산(공용 계산 패키지)은 입력 중 미리보기용
- 기기 = 캐시: 데스크톱 앱은 암호화 로컬 저장소에 마지막으로 받은 데이터 보관, 웹은 탭이 열려 있는 동안만 메모리에 보관
- 저장 흐름: 입력 → 화면에 바로 반영(저장 중 표시) → 서버 확정 → 모두 저장됨. 서버가 거절하면 원래 값으로 되돌리고 이유 한 줄 표시
- 실시간 반영: 앱·웹이 열려 있는 동안 서버와 웹소켓 연결 유지, 상대 변경을 1\~2초 안에 받음. 연결이 안 되면 30초 간격 확인(폴링)으로 대체
- 재연결: 마지막으로 받은 변경 번호 이후 변경만 받아 반영(전체 다시 받기 없음)
- 상대 변경 표시: 보고 있는 화면의 값이 바뀌면 바로 교체 + 바뀐 칸 2초 강조. 입력 흐름 중이면 지금 질문의 값은 그대로 두고 관련 값만 갱신
- 버전: 모든 레코드에 버전 번호. 저장 요청은 ‘화면을 열 때의 버전’을 함께 보내 서버가 충돌 여부 판정
- 저장 상태 표시(→ 화면 설계 › 이번 달 › 앱 기본 틀): 두 사람 아바타에 마우스를 올리면 툴팁 “모두 저장됨” / “저장 중”, 오프라인은 Banner(기기에 저장됨) + 보낼 입력이 있으면 ‘대기 {n}건’

## 2. 데이터 유형별 충돌 규칙

실시간 반영으로 대부분 충돌은 생기지 않음. 서버 판정 기준은 필드 단위: 다른 필드끼리는 자동 합침, 같은 필드만 아래 규칙. 제안 자체의 규칙(72시간·함께 정하기·제안 상태)은 → 핵심 규칙 › 부부·제안·권한.

| 유형 | 예 | 동시에 바뀌면 | 사용자에게 보이는 것 |
| --- | --- | --- | --- |
| 사실값 | 내 수입, 월급날, 고정지출 금액, 자산·부채 금액·잔액 | 마지막 저장 우선. 단, 상대가 1분 안에 같은 필드를 다른 값으로 바꿨으면 나중 저장한 사람에게 선택 화면. 저장 즉시 안 나눈 돈 재계산 | 덮인 쪽에 토스트 “{이름}님이 방금 {항목}을 바꿨어요”. 선택 화면 “{이름}님이 방금 이 값을 바꿨어요. 어느 쪽으로 할까요?” |
| 사실값 중 수입 | 월 실수령, 기간 수입 변경 | 내 소유라 상대와는 충돌 없음, 내 기기 둘(앱·웹) 사이만. 저장 직전 서버 최신 값 재확인, 화면을 연 뒤 바뀌었으면 저장 전 확인(수입 변경은 즉시 알림이라 잘못 저장 방지) | “다른 기기에서 월 수입이 {금액}으로 바뀌었어요. 이 값으로 바꿀까요?” |
| 배분 결정 | 용돈, 분담 방식, 공동 목표, 생활비·양가 비용·결혼 비용 예산 | 제안으로만 바뀌어 값에 직접 충돌 없음. 동시 제안·응답·철회와 제안 기준 값 변경 처리 → 핵심 규칙 › 부부·제안·권한 6-7 | 문구 → 핵심 규칙 › 부부·제안·권한 6-7 |
| 월급 나누기 | W-02 플랜 줄 ‘옮겼어요’ / ‘다른 금액을 옮겼어요’ | 플랜 줄 단위 합치기(다른 줄 체크는 서로 영향 없음). 체크는 담당자 또는 ‘대신 체크’(배우자 몫), ‘비상금 → 공동 생활비’ 줄은 담당 = 같이라 누구나. 같은 줄을 둘이 체크하면 먼저 도착한 체크 유지. 금액이 다르면 마지막 저장 우선 + 이력 | “이미 {이름}님이 체크했어요” / 금액이 덮인 쪽에 토스트 “{이름}님이 방금 나누기 금액을 바꿨어요” |
| 기록 | 챙길 날 기록(Y-08), 목표 사용, 결혼 비용 ‘결제했어요’, 메모·사진 | 추가형이라 새 기록끼리는 충돌 없음(둘 다 저장). 같은 기록을 동시에 고치면 필드 단위 마지막 저장 우선 + 변경 이력 | 덮인 쪽에 토스트 “{이름}님이 방금 {기록}을 고쳤어요” |
| 삭제 vs 수정 | 한 사람이 삭제, 다른 사람이 같은 항목 수정 | 삭제 우선. 삭제 항목은 휴지통에 30일 보관(→ 화면 설계 › 설정 ‘휴지통’), 늦게 도착한 수정은 휴지통 항목에 반영해 복구 시 살아남음 | 수정한 쪽: “{이름}님이 방금 {항목}을 지웠어요” + ‘되살리기’ 버튼(되살리면 상대에게 배우자 활동 표시) |

- ‘이번 달만 바꾸기’(W-01)·W-03c ‘내 용돈에서’ = 즉시 적용이라 사실값 규칙 따름
- 권한 밖 저장(상대 명의 항목, 해제 대기 중 제안 등)은 서버가 거절 → “{배우자}님 항목이라 볼 수만 있어요” 등(문구 → 화면 설계 › 공통 상태)

## 3. 월말 정리 동시 진입

정리는 한 번에 하나만 진행. 먼저 시작한 사람이 정리자, 상대는 같이 하거나 보기만.

| 상황 | 처리 | 화면 |
| --- | --- | --- |
| 한 사람이 정리 중, 상대가 W-04 진입 | 선택지 2개 | “{이름}님이 정리 중이에요” — ‘같이 하기’ / ‘보기만’ |
| 같이 하기 | 함께 모드 시작(두 계정 동시 접속, 웹 가능). 단계 화면 동기(누가 ‘다음’을 눌러도 둘 다 이동), 입력은 누구나, 같은 칸은 마지막 저장 우선. W-04h에서 바꾼 값은 바로 확정(‘함께 정하기’ 항목 포함, 표시 해제) | 상단에 두 사람 프로필 + “함께 정리 중”. 상대가 입력 중인 칸에 “{이름}님이 입력 중” |
| 보기만 | 읽기 전용, 정리자 화면을 따라 이동. 언제든 ‘같이 하기’로 전환 가능(전환 시점부터 함께 모드) | “보기만 하는 중이에요” + ‘같이 하기’ 버튼 |
| 함께 모드 중 한 사람이 나감·연결 끊김 | 그때까지 확정된 값 유지. 남은 사람이 이어서 하면 이후 바뀐 값은 혼자 정리 규칙(‘월말 정리 제안’ 묶음). 5분 안에 돌아오면 함께 모드 재개 | “{이름}님이 나갔어요. 이제부터 바꾸는 값은 제안으로 보내요” |
| 혼자 정리 중 상대가 사실값 변경 | 사실값은 즉시 반영. 그 값을 쓰는 단계(꼼꼼 모드 W-04b 잔액 예상, W-04g 정산 요약, W-04h 조정)를 다시 계산 | “{이름}님이 {항목}을 바꿨어요. 결과를 다시 계산했어요” |
| 둘이 거의 동시에 시작 | 서버 도착 순서로 정리자 결정, 나중 사람은 위 선택지 화면으로 | 위와 같음 |

- 혼자 정리 중 상대가 제안 응답·월급 나누기 등 다른 작업은 그대로 가능
- 정리 화면을 연 채 30분 동안 입력이 없으면 정리자 잠금 해제(입력값은 저장 유지), 상대가 이어서 정리 가능
- 정리 기간 전에 미리 적은 W-04j·W-04k 값은 초안(month\_close.status)으로 저장. 두 사람이 같은 항목을 동시에 적으면 항목별로 나중 저장이 이기고 Toast로 알림(→ 화면 설계 › 월말 정리 W-04j)

## 4. 오프라인

데스크톱 앱만 오프라인 입력 지원, 웹은 미지원. 여기서는 동작만 정하고, 사용자에게 보이는 상태 문구는 → 화면 설계 › 공통 상태.

| 구분 | 데스크톱 앱 | 반응형 웹 |
| --- | --- | --- |
| 조회 | 마지막으로 받은 데이터 전체 조회 + 마지막 저장 시각 표시 | 불가(연결 끊김 안내) |
| 입력 가능 | 사실값 수정, 월급 나누기, 기록 추가·수정, 이번 달만 바꾸기 | 입력 중이던 화면만 탭 메모리에 임시 저장, 연결되면 자동 전송(탭을 닫으면 삭제) |
| 입력 불가(비활성 + 안내) | 제안 보내기·응답·철회, 월말 정리 시작·확정, 초대·연결 해제, 공개 범위 변경, 구독 결제 | 전체 |

- 대기열: 입력은 기기에 순서대로 저장(암호화), 연결되면 순서대로 전송. 저장 상태에 대기 건수 표시
- 전송 시 충돌은 2장 규칙. 단, 대기 중 입력이 상대가 그 뒤에 바꾼 값을 덮게 되면 자동으로 덮지 않고 어느 값으로 할지 확인(문구 → 화면 설계 › 공통 상태)
- 서버가 거절한 입력(항목 삭제됨, 권한 바뀜, 정리 끝난 달)은 ‘보내지 못한 입력 {n}건’ 목록 → 다시 하기 / 버리기
- 7일 넘게 오프라인이면 재연결 때 대기 목록을 먼저 보여주고 한 번에 보내기
- 입력 시각은 기기 시각이 아니라 서버 도착 시각으로 처리(사이클·기준일 판단 포함), 이력에는 기기 입력 시각도 함께 저장

## 5. 서버 작업과 사용자 편집이 겹칠 때

서버 작업은 시작 시각의 스냅샷으로 계산, 그 뒤 도착한 편집은 작업이 끝난 결과 위에 반영하고 안 나눈 돈 재계산.

| 서버 작업 | 스냅샷 기준 | 작업 중·후 편집 처리 |
| --- | --- | --- |
| 기준일 0시 플랜 생성 | 0시 직전까지 서버에 도착한 확정 값·적용될 제안 | 작업 중(수 초) 도착한 편집은 대기 후 새 플랜에 반영, 안 나눈 돈 재계산. 지난 플랜은 읽기 전용이라 반영 안 함. 화면 “새 플랜을 만들고 있어요”, 입력은 막지 않음 |
| 기준일 제안 묶음 적용(재계산) | 0시 직전까지 도착한 응답. 월말 정리 제안 마감(전날 23시 59분)도 서버 도착 시각 기준 | 0시 이후 도착한 ‘반대’ 처리 → 핵심 규칙 › 부부·제안·권한 6-7 |
| 자동 나누기 줄 추가(‘목표자금 → 공동 생활비’) | 기록이 서버에 도착한 시각의 사이클 | 이번 사이클 정리를 이미 끝냈으면 다음 사이클. 플랜 생성 중 도착하면 새 플랜에 추가 |
| 연결 해제 대기 중 기준일 | 지난 플랜 그대로 연장(새 제안 적용 없음) | 연장된 플랜에서 월급 나누기·기록·월말 정리 가능(→ 핵심 규칙 › 부부·제안·권한 1장), 해제 확정 시 사이클 종료 |
| 변동 수입 미응답 처리(W-04a2) | 기준일 전날까지 응답 없음 → 기준 수입대로 | 그 뒤 들어온 응답은 ‘정리 고치기’(7일 이내)로 반영 |

- 서버 작업은 부부 공간 단위로 한 번에 하나만 실행(겹치면 대기)
- 작업이 실패하면 지난 값 유지 + 재시도, 사용자 화면은 “잠시 문제가 생겼어요” 대신 지난 플랜을 그대로 표시

## 6. 버전·호환

- 데스크톱 앱: 자동 업데이트(→ 기술·운영 5장). 서버가 ‘최소 지원 버전’ 관리
  - 최소 지원 버전 이상: 백그라운드 다운로드 후 다음 실행 때 적용, “새 버전이 준비됐어요” + 지금 다시 시작
  - 최소 지원 버전 미만: 동기화 중단, 업데이트 화면만 표시(조회는 가능, 대기열은 보존했다가 업데이트 뒤 전송)
  - 최소 지원 버전은 데이터 구조·계산 규칙이 호환되지 않게 바뀔 때만 올림
- 웹: 항상 최신. 열린 탭은 새 배포를 받으면 “새 버전이 있어요” + 새로고침(입력 흐름 중이면 끝난 뒤 표시)
- 데이터 구조 변경: 추가형 우선(필드 추가, 구버전은 모르는 필드를 지우지 않고 보존). 이름 변경·삭제는 2단계(새 필드에 같이 쓰기 → 지원 버전이 모두 새 필드를 읽은 뒤 옛 필드 제거)
- 이전(마이그레이션)은 서버에서 실행. 기기 캐시는 앱 업데이트 때 변환, 실패하면 대기열을 먼저 보낸 뒤 캐시를 지우고 서버에서 다시 받음
- 계산 규칙이 바뀌면 서버 값이 기준, 이미 정리 끝난 달의 결과는 다시 계산하지 않음

## 7. 변경 이력

- 대상: 모든 항목의 필드 변경. 기록 = 항목, 필드, 전·후 값, 바꾼 사람, 서버 저장 시각(+ 오프라인이면 기기 입력 시각), 기기 종류(데스크톱/웹), 출처(직접 수정 / 월말 정리 / 제안 적용 / 대신 체크 / 서버 작업 / 오프라인 대기열 / 충돌 선택)
- 배우자 활동(H-08): 이 이력에서 상대가 바꾼 것만 표시. 공개 범위 따름: ‘합계만’ 항목은 이름 없이 “개인 자산 금액이 바뀌었어요”, ‘비공개’·서프라이즈 항목은 표시 안 함
